# Корректировка промпта: все пункты `missing_data` в следующем шаге

- **Дата:** 26 октября 2026 года
- **Основание:** повторный прогон пяти сценариев, [TEST_PROTOCOL_IMPROVEMENTS.md](TEST_PROTOCOL_IMPROVEMENTS.md)
- **Затронутые файлы:** `prompt.js`, `gigachat.js`, `test/gigachat.test.js`
- **Проверка:** `npm test` — 38 из 38

## Что показал прогон

В сценарии «Недостаточно данных» (сделка №55) модель заполнила `missing_data` пятью пунктами:

```text
контактное лицо
контакт для связи
бюджет
сроки
точное количество
```

А `next_step` назвал только четыре:

```text
Уточнить у клиента контактное лицо, способ связи, бюджет и сроки.
```

«Точное количество» в следующем шаге отсутствовало, хотя менеджеру без него не рассчитать стоимость. Черновик ответа при этом количество упоминал — то есть модель понимала пропуск, но не перенесла его в план действия.

Причина в промпте: требование перечислять в `next_step` было сформулировано только для бюджета и сроков. Модель выполняла правило буквально и не воспринимала остальные пункты `missing_data` как обязательные.

## Корректировка 1 — полный список токенов

### Было

```text
8. Персональные данные в заявке заменены служебными токенами вида
[ИМЯ_1], [ТЕЛЕФОН_1], [EMAIL_1], [АДРЕС_1], [КОМПАНИЯ_1], [ПАСПОРТ_1].
Это реальные данные. Не раскрывай, не переводи, не переписывай и не придумывай
вместо них другие значения...
```

### Стало

```text
8. Персональные данные и реквизиты в заявке заменены служебными токенами вида
[ИМЯ_1], [ТЕЛЕФОН_1], [EMAIL_1], [АДРЕС_1], [КОМПАНИЯ_1], [ПАСПОРТ_1],
[ИНН_1], [ОГРН_1], [КПП_1], [СЧЁТ_1].
Это реальные данные. Не раскрывай, не переводи, не переписывай и не придумывай
вместо них другие значения...
```

### Зачем

После усиления анонимизации в промпт уходят четыре новых типа токенов. Раньше модель видела `[ИНН_1]`, но не знала, что это служебная метка реальных реквизитов. Формально правило «не выдумывай данные» работало, но модель могла:

- посчитать реквизиты отсутствующими и добавить в `missing_data` лишние пункты;
- попытаться «расшифровать» токен и выдать предположение вместо реального значения.

Теперь все десять типов токенов перечислены явно, и правило «токен означает, что данные указаны» распространяется на реквизиты.

## Корректировка 2 — `next_step` покрывает весь `missing_data`

### Было

```text
- next_step — одно конкретное действие менеджера. Если missing_data не пуст,
  укажи, какие именно данные нужно уточнить, и перечисли бюджет и сроки,
  если они есть в missing_data (например, «Уточнить у клиента бюджет, сроки
  и адрес доставки»).
```

### Стало

```text
- next_step — одно конкретное действие менеджера. Если missing_data не пуст,
  перечисли в next_step все пункты из missing_data без пропусков, включая
  «точное количество», контактное лицо и контакт для связи, если они там есть
  (например, «Уточнить у клиента бюджет, сроки и точное количество»).
  Не ограничивайся бюджетом и сроками, если в missing_data есть другие пункты.
```

Дополнительно уточнено описание поля в JSON-схеме:

```text
'Одно конкретное действие менеджера; если missing_data не пуст —
 со всеми пунктами из него.'
```

### Зачем

Старая формулировка задавала два обязательных пункта — бюджет и сроки — и не запрещала пропустить остальные. Новая формулировка:

- требует перечислить **все** пункты `missing_data`;
- явно называет самые частые пропуски: количество, контактное лицо, контакт для связи;
- запрещает ограничиваться бюджетом и сроками.

## Страховка в коде

Промпт — недетерминированная инструкция. Даже с новым текстом модель может сократить список, поэтому в `gigachat.js` добавлена детерминированная проверка `ensureNextStepClarifications`.

### Было

```js
const asks = [];
const hasBudget = missing.some((item) => item.toLowerCase().includes('бюджет'));
const hasDeadline = missing.some((item) => item.toLowerCase().includes('срок'));

if (hasBudget && !/бюджет/i.test(nextStep)) asks.push('бюджет');
if (hasDeadline && !/срок/i.test(nextStep)) asks.push('сроки');
```

Проверялись только бюджет и сроки.

### Стало

```js
const unmentioned = missing.filter((item) => !isMentionedInNextStep(nextStep, item));
if (!unmentioned.length) return nextStep;

const base = String(nextStep || '').trim().replace(/[.!?]+$/, '');
if (/^уточнить/i.test(base)) return `${base}, а также ${joinRu(unmentioned)}.`;
return `Уточнить у клиента ${joinRu(unmentioned)}.`;
```

`isMentionedInNextStep` сопоставляет пункт `missing_data` с формулировками следующего шага по словарю синонимов:

| Пункт `missing_data` | Что считается упоминанием в `next_step` |
|---|---|
| бюджет | «бюджет» |
| сроки | «срок», «к какому», «когда», «дата» |
| точное количество | «количество» |
| контактное лицо | «контактное», «лицо», «имя» |
| контакт для связи | «контакт», «связь», «телефон», «почта», «e-mail» |
| компания | «компания» |
| адрес доставки | «адрес» |
| продукт или услуга | «продукт», «товар», «мебель» |

Если пункт не упомянут, он дописывается в конец шага. Если шаг начинается не с «Уточнить», он заменяется на «Уточнить у клиента …» — это сохраняет прежнее поведение и оставляет одно конкретное действие.

## Проверка на реальном ответе сделки №55

Ниже — фактический ответ модели из сделки №55, пропущенный через `normalizeResult` после корректировки.

**До корректировки (что записано в CRM):**

```text
missing_data: контактное лицо, контакт для связи, бюджет, сроки, точное количество
next_step:    Уточнить у клиента контактное лицо, способ связи, бюджет и сроки.
```

**После корректировки:**

```text
missing_data: контактное лицо, контакт для связи, бюджет, сроки, точное количество
next_step:    Уточнить у клиента контактное лицо, способ связи, бюджет и сроки,
              а также точное количество.
```

Дописывание сработало и на исходном ответе модели, без повторного запроса в GigaChat: страховка не зависит от того, насколько удачно сформулировал `next_step` сам модель.

## Живая проверка после корректировки

Тот же текст заявки отправлен в GigaChat повторно уже с новым промптом (модель `GigaChat-2-Max`, 8,4 с). Сделка и журнал при этой проверке не создавались: вызывался только слой анализа.

```text
missing_data: точное количество, контактное лицо, контакт для связи, бюджет, сроки
next_step:    Уточнить у клиента точное количество, контактное лицо и контакт
              для связи, а также бюджет и сроки.
```

Все пять пунктов `missing_data` названы в следующем шаге. Черновик ответа при этом остался коротким: два уточняющих вопроса — количество и контакт, бюджет и сроки.

## Тесты

Добавлены два теста в `test/gigachat.test.js`:

1. **«дополняет next_step пропущенным точным количеством»** — модель вернула `missing_data` из бюджета, сроков и расплывчатого количества, а `next_step` назвал только бюджет и сроки. Ожидание: в шаге появляется «а также точное количество», порядок `missing_data` сохраняется.
2. **«не переписывает next_step, если все пункты уже названы»** — если шаг уже содержит все пункты, текст остаётся дословно прежним. Это защищает от лишних изменений формулировки модели.

## Границы корректировки

- Страховка работает только для целевого лида без `needs_human`. Для жалоб и нецелевых запросов `next_step` фиксированный и не должен превращаться в список уточнений.
- Словарь синонимов покрывает восемь стандартных полей. Если в `missing_data` появится нестандартный пункт, он будет добавлен в шаг как есть — это безопаснее, чем потерять его.
- Промпт по-прежнему просит 1–2 уточняющих вопроса в `reply_draft`, а не перечисление всех пунктов. Черновик остаётся коротким; полный список живёт в `next_step` и в блоке «Чего не хватает».
- Корректировка не решает проблему дедупликации контакта между компаниями (сделка №57). Это отдельное ограничение модели данных, описано в протоколе.
